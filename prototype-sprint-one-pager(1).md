> Working document for building the first public-facing website and refining the service.

## 1. Core Concept

**Prototype Sprint** is a live, collaborative product-building service for founders, small teams, nonprofits, ministries, and other idea-stage builders who want to turn an idea into something tangible quickly.

The core offer is not traditional consulting and it is not a promise to deliver a fully finished software product in three hours.

It is a **focused 3-hour working session where discovery, decision-making, design, AI-assisted development, and iteration happen together in real time.**

### Working headline

# From idea to something real in one focused session.

### Supporting copy

Bring an idea, a problem, or an early concept. We will clarify what matters, choose the highest-value outcome, and start building it together live.

When the idea is focused and the preparation is strong, a first sprint can potentially end with a **deployed prototype, a live landing page, or even both**.

The goal is to move quickly without pretending every idea has the same scope.

### Primary CTA

**Book a Prototype Sprint — $500 / 3 hours**

Secondary CTA:

**See what we can build**

## 2. The Promise

The promise should be ambitious without guaranteeing a specific quantity of work.

### Core promise

**Get as far as we responsibly can toward something you can use, test, share, or demonstrate.**

### Important positioning

We should communicate:

- We build during the session.
- The client participates in decisions.
- AI-assisted development lets us move very quickly.
- Preparation directly affects how far we can get.
- A deployed first version is a legitimate target for the initial sprint.
- A deployed product is not guaranteed.
- A prototype is not automatically production-ready software.
- The session is constrained by time, not by an artificially fixed list of deliverables.

### Professional version of “if you have all your shit together”

> If you arrive with a focused concept, prepared content and assets, access to the services we will need, and the ability to make decisions quickly, we can aim aggressively toward a deployed first version during the initial sprint.

Follow with:

> That is a target, not a guarantee. Every idea has different technical and creative requirements, so we prioritize the most valuable outcome and use the session accordingly.

## 3. How the Sprint Works

The sprint is **live and collaborative**.

This should be a prominent visual section on the website.

### 1. Focus

We identify:

- What are we building?
- Who is it for?
- What problem does it solve?
- What is the smallest useful version?
- What outcome would make this sprint a win?
- Which pieces matter now?
- Which pieces can be mocked, simplified, or deferred?

### 2. Build

We begin implementing immediately.

Depending on the project, this may involve:

- user flows
- interface design
- web development
- database setup
- authentication
- integrations
- landing page development
- copy
- brand implementation
- deployment

The client sees the work as it happens and can make decisions in real time.

### 3. Refine

We test the primary workflow, fix obvious issues, improve the most important surfaces, and decide how to use the remaining time.

### 4. Ship / Handoff

When practical, we deploy what we built.

The client receives the work created during the sprint and leaves with a clear understanding of:

- what works
- what is mocked
- what is incomplete
- what should happen next

The point of the service is not to debate stacks during every session.

The default stack should be intentionally boring, fast, transferable, and founder-owned.

## Frontend

Default:

- React
- TypeScript
- Vite
- Tailwind CSS
- reusable component system as appropriate

Goals:

- extremely fast setup
- easy AI-assisted iteration
- responsive by default
- straightforward handoff
- no unnecessary framework complexity for prototypes

## Source Control

Default:

- GitHub
- client-owned repository whenever practical

## Deployment

Default client prototype target:

- **Netlify**

Netlify currently provides a Free plan suitable for many prototype-scale deployments.

Avoid using Vercel Hobby as the standard client/commercial hosting option because Vercel currently defines Hobby as personal, non-commercial use.

Vercel may still be appropriate when the client is on an eligible paid commercial plan.

## Database / Backend

Default:

- **Supabase**

Why:

- Postgres
- authentication
- data APIs
- storage
- realtime
- functions
- good prototype velocity
- Free plan available for appropriate early-stage usage

## Authentication

Default preference when login is required:

- Supabase Auth
- email/password, magic link, or social auth depending on the product

For Google login:

- Google Cloud / Google Auth Platform OAuth credentials
- Google Workspace is not required solely for OAuth

## Payments

Default:

- Stripe
- use test mode during prototype work unless the scope specifically includes production payment setup

## Analytics

Use lightweight analytics when valuable.

Potential options:

- Netlify analytics/features where appropriate
- Google Analytics
- PostHog
- other client-preferred analytics

Do not consume meaningful sprint time on analytics unless measurement is part of the sprint goal.

## Domain

Client should own and control the domain.

If the founder wants a custom domain live during the sprint, registrar/DNS access should be ready beforehand.

# 14. Prototype vs Production

We need an explicit boundary.

### Suggested copy

> Prototype Sprints are designed for validation, experimentation, demos, early users, stakeholder conversations, and product learning. Unless production readiness is specifically scoped, sprint deliverables should not automatically be treated as production-grade software.

Production work may require additional attention to:

- security
- privacy
- performance
- accessibility
- testing
- monitoring
- backups
- compliance
- data retention
- billing
- error handling
- infrastructure
- scalability
- legal requirements

### Not ideal for a single sprint

Examples:

- complex legacy migrations
- highly regulated systems
- sensitive production data
- large enterprise integrations
- deep security/compliance requirements
- production-critical financial systems
- complex native mobile applications
- projects where no decision-maker is available
- projects dependent on unresolved third-party access

These projects may still begin with a sprint, but the sprint should be used for discovery, architecture, interface prototyping, or proof of concept rather than pretending the whole product will be completed.

# 17. Suggested Public FAQ

## Can you really build something in three hours?

Sometimes, yes — and occasionally more than people expect.

The result depends on scope, complexity, preparation, and how quickly decisions can be made. Simple, focused ideas can move from concept to deployed prototype surprisingly quickly. More complicated ideas may use the sprint to establish the core workflow or proof of concept.

## Is a deployed prototype guaranteed?

No.

Deployment is often a realistic target, particularly for well-prepared web-based projects, but the sprint guarantees dedicated working time rather than a predetermined quantity of software.

## Could we build a prototype and landing page in the same sprint?

Yes, when the scope is focused and the necessary content, assets, and accounts are ready.

For a more complex product, we may decide that the best use of the sprint is to focus entirely on the application and handle the landing page in a subsequent session.

## Do I need to know how to code?

No.

You need to know the problem you are trying to solve and be willing to make decisions. The technical implementation is handled during the sprint.

## Do I need everything figured out beforehand?

No.

Discovery is part of the session. However, the more uncertainty we resolve before the sprint, the more time we can spend building.

## Do I own the code?

The intention is yes: work should be built in client-owned accounts and repositories whenever practical, subject to any third-party licenses or services used.

Final contract language should define ownership precisely.

## Can you help with branding too?

Yes.

A lightweight brand starter can be part of a sprint when scope allows, or branding can be the focus of its own session.

## Can you help me launch on social media?

Yes.

Launch messaging, profile setup, content planning, initial social assets, and a starter launch plan can be included as sprint priorities or handled in a dedicated launch sprint.

## Is this production-ready software?

Not automatically.

The sprint is optimized for speed, validation, demos, and early product development. Production hardening should be separately evaluated and scoped.

## What happens after the first sprint?

You can take the work and continue independently, bring it to another developer, or book an iteration session with us.

There is no requirement to continue.

# 24. Internal Delivery Philosophy

These are operator principles and do not all need to appear publicly.

## Default to one stack

Speed comes from repetition.

Avoid reinventing architecture unless the project actually needs something different.

## Client-owned infrastructure

Create work in the client's accounts whenever possible.

## Functional before ornamental

Get the key workflow working before spending a large portion of the sprint polishing low-value details.

## Mock intentionally

If a backend, integration, or workflow is too large for the sprint, mock it clearly rather than building a fragile half-solution.

## Label reality

At handoff, explicitly distinguish:

- functional
- prototype-only
- mocked
- placeholder
- requires production work

## Ship when useful

Deployment is valuable because it turns the project into something the client can send to another person immediately.

Do not waste half the session on deployment infrastructure when a local/shareable prototype better serves the actual goal.

## Protect the clock

Account creation, forgotten passwords, missing API access, indecision, copywriting, and asset hunting consume sprint time.

This is why readiness is part of the product.

# 25. Tech Account Checklist — Internal Reference

As of **August 2026**, the default recommendations are:

### GitHub
Create a client-owned account/repository.

Preferred default deployment platform for commercial/client prototypes that fit the current Free plan.

Preferred default backend for many prototypes. A Free plan is available and bundles Postgres, auth, APIs, storage, and other backend capabilities.

Client-owned account. Prototype with test mode unless live payments are deliberately in scope.

### Domain
Client-owned registrar account with DNS access ready before the sprint if same-day custom-domain deployment is a priority.
